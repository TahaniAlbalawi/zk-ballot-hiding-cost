# What does hiding the ballot cost? Code, data and artifacts

This repository accompanies the article *What Does Hiding the Ballot Cost? Information Symmetry and Trust in Zero-Knowledge Voting on Ethereum*. It contains:

- the circuits, contracts and measurement harness;
- the raw measurements of every run (342 runs, 39,168 ballots);
- the scripts that turn those measurements into every table, figure and number in the article;
- the supplementary tables (Tables S1–S7).

The compiled circuits, the generated proving and verification keys and the powers-of-tau file are too large for Git. They are archived together with this repository on Zenodo: https://doi.org/10.5281/zenodo.24368648.

> **Research prototype.** This code measures costs on a local chain. It uses a single-contributor Groth16 setup, has no formal verification, and provides neither coercion resistance nor receipt-freeness. Do not use it for real elections. All voters, credentials, votes and keys are synthetic.

## What is compared

Three voting workflows share one eligibility core: a Merkle membership proof, a nullifier, and a binding of the proof to the sending account, all proved with Groth16. They differ in what the ballot carries and in how the result is produced.

| Name in the article | Identifier in code and data | Ballot on chain | Result |
|---|---|---|---|
| Public | `PUBLIC_DISCLOSURE` | the vote | recomputed from `VoteCast` events |
| Publisher | `COMMITMENT_BALLOT_HIDING` | Poseidon(vote, randomness) | openings reconciled off chain; counts published by a configured publisher |
| Reveal | `COMMITMENT_ONCHAIN_REVEAL` | Poseidon(vote, randomness) | openings revealed and checked on chain, then finalized |

Some identifiers keep names from an earlier design:
- the Solidity names `EncryptedVoteCast`, `encryptedBallots` and `PRIVATE_ENCRYPTED`;
- the script `tallyEncrypted.ts`.

The stored object is always a hash commitment, never a ciphertext.

## Reproducing the results

There are three levels. Each level needs more software and time than the one before.

### Level 1: re-derive every number from the raw measurements

This level needs only Python 3.9 or later and takes about a minute. From the repository root:

```bash
python3 -I analysis/paper_analysis.py data/full-2026-11
python3 -I analysis/crosscheck_stats.py data/full-2026-11
python3 -I analysis/make_paper_tables.py data/full-2026-11 paper
git status --short    # no changes expected
```

What each step does:
- `crosscheck_stats.py` recomputes all 144 paired contrasts and their Holm adjustments from `runs.jsonl`, with code independent of the harness. It exits with an error on any mismatch.
- The other two scripts regenerate the files that the article's tables and figures are built from.

### Level 2: check the archived circuits and keys

Download the artifacts archive and `SHA256SUMS` from the Zenodo record into the repository root, then:

```bash
grep artifacts SHA256SUMS | shasum -a 256 -c
tar -xzf zk-ballot-hiding-cost-v0.3.0-artifacts.tar.gz
shasum -a 256 -c circuits/build/ARTIFACTS_SHA256SUMS
python3 -I analysis/zkey_size_model.py circuits/build/configurations
python3 -I analysis/make_supplementary.py data/full-2026-11 circuits/build/configurations supplementary
python3 -I analysis/check_source_manifest.py data/full-2026-11/environment-1794421809965.json .
```

What these commands check:
- **Archive layout.** The archive restores `circuits/build/` and `contracts/contracts/cmc_verifiers/`. These hold the exact keys and verifier contracts used in the experiment, and the powers-of-tau file.
- **Key sizes.** `zkey_size_model.py` checks the key-size equation of the article against all 24 keys.
- **Sources.** `check_source_manifest.py` confirms that the circuits, contracts, library and harness in this repository are byte-identical to those recorded with the run.

With Node.js installed (see Level 3), the archived keys can also be checked end to end:

```bash
npm ci
npm run contracts:compile
npm run circuits:test     # every key against its R1CS and the powers of tau; one full proof
npm run contracts:test    # contract tests, including real proofs bound to the sender
```

### Level 3: rerun the experiment

1. **Install the toolchain.**
   - Node.js 22.10.0 with npm 10.9.0: `nvm install` reads `.nvmrc`.
   - Circom 2.2.2 is needed only to rebuild the circuits.
   - Then run `npm ci`.
2. **Provide circuits and keys.** Either extract the Zenodo archive (Level 2), which gives the exact keys used in the article, or rebuild them with `npm run circuits:build`. A rebuild runs a new single-contributor setup with a fresh random beacon. The new keys differ from the archived ones, but constraint counts, domain sizes and key sizes are identical.
3. **Compile the contracts:** `npm run contracts:compile`.
4. **Run a design.**
   ```bash
   npm run experiment -- evaluation/v3/designs/pilot.json data/my-pilot   # a few minutes
   npm run experiment -- evaluation/v3/designs/full.json data/my-full     # 6 h 16 min on an Apple M1 Pro
   npm run analyze -- data/my-full
   ```
   The runner starts a local Hardhat node when none is listening on port 8545.
   - It appends one complete block at a time, so an interrupted run resumes at the first incomplete block.
   - Keep the machine otherwise idle during timing runs.
5. **Analyze the run** with the Level 1 scripts, giving the new directory instead of `data/full-2026-11`.

What a rerun reproduces:
- **Machine-dependent:** timing and memory.
- **Identical:** constraint counts, key sizes, and execution gas.
- **Nearly identical:** calldata gas differs by a few multiples of 12 gas, because the number of zero bytes in proofs and timestamps varies.

As a check, the pilot design was rerun from this release on the original machine. Votes, result counts, verifier gas, deployment gas, and cast gas net of calldata were identical in all 18 runs.

### Optional: command-line demo

The `scripts/` package can also run single elections by hand on a local node, using the depth-5 configuration (`D05-C04`).
- **Prerequisites:** the circuits and keys in place (Level 2 or 3) and the contracts compiled.
- **Start a node** with `npm run contracts:node`, then run the commands below in a second terminal at the repository root.

First, create the synthetic voters. Their secrets stay in `scripts/data/`.

```bash
npm run setup-electorate
B=$PWD/circuits/build/configurations/D05-C04
```

**Public:**

```bash
CMC_CONFIGURATION_ARTIFACT_MANIFEST=$B/public/configuration-artifact-manifest.json npm run deploy
VOTER_INDEX=0 VOTE=2 npm run demo-cast
```

**Publisher.** After the vote, close the voting window on the local chain, then reconcile the openings and publish the counts:

```bash
CMC_CONFIGURATION_ARTIFACT_MANIFEST=$B/commitment/configuration-artifact-manifest.json npm run deploy-private
VOTER_INDEX=1 VOTE=1 npm run demo-cast-private
curl -s -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"evm_increaseTime","params":[3600]}' http://127.0.0.1:8545
curl -s -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":2,"method":"evm_mine","params":[]}' http://127.0.0.1:8545
ALLOW_LOCAL_SECRET_RELEASE=1 npm run tally
```

**Reveal.** After the vote, advance the local chain past the deadlines, reveal the openings on chain, and finalize:

```bash
COMMITMENT_WORKFLOW=ONCHAIN_REVEAL CMC_CONFIGURATION_ARTIFACT_MANIFEST=$B/commitment/configuration-artifact-manifest.json npm run deploy-private
VOTER_INDEX=2 VOTE=0 npm run demo-cast-private
ADVANCE_LOCAL_CHAIN_TIME=1 FINALIZE=1 npm run reveal
```

Without `CMC_CONFIGURATION_ARTIFACT_MANIFEST`, the deploy scripts fall back to the generic `Verifier.sol` and `VerifierPrivate.sol`. Those do not match the `D05-C04` keys, so the casts are rejected with `InvalidProof()`.

## Environment of the reported run

| Component | Version or setting |
|---|---|
| Host | Apple M1 Pro (10 cores), 16 GiB memory, macOS 26.5.2 (Darwin 25.5.0) |
| Node.js / npm | 22.10.0 / 10.9.0 |
| Circom | 2.2.2, default simplification (`--O1`); circomlib 2.0.5 |
| Proving | snarkjs 0.7.5 (Groth16, BN254); circomlibjs 0.1.7 |
| Powers of tau | `ppot_0080_14.ptau` from the PSE Perpetual Powers of Tau ceremony (SHA-256 `3ca1149e9349b22b0ee0649399cfb787677129b7b1189d1899fc0d615d9583db`) |
| Chain | Hardhat 2.28.3 local node, Cancun rules, automatic mining; ethers 6.16.0 |
